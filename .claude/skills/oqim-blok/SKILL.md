# Adding a block type

A block type is enumerated in about a dozen places across both applications and
the compiler catches exactly **one** of them. The rest fail silently, at run
time, in front of a customer. This file is the list, so nobody has to rediscover
it by grepping `NodeType` through seventeen files again.

The comment at the top of `features/flows/types.ts` says adding a type means
"adding an entry to node-registry and nothing else". That was true once. It is
not true now, and it is not the file to trust — this one is.

## The list

Start at the union, end at the runtime. Nothing below is optional unless it says
so.

**1. `frontend/src/features/flows/types.ts` — the `NodeType` union.**
The contract between the two sides: the backend stores whatever string the
editor writes and serialises it back untouched. Say in the comment why this is a
type and not a setting on an existing block — every member there carries that
argument, and the reviewer's first question is "why is this not a Xabar".

**2. `frontend/src/features/flow-builder/node-definitions.ts` — `NODE_TYPE_DEFINITIONS`.**
The one enumeration the compiler enforces: it is `Record<NodeType,
NodeTypeDefinition>`, so a union member with no entry fails `npm run typecheck`.
Height, colour, palette label, the `hasX` capability flags the Inspector reads,
and `ports`. Everything else on this page is silent when missed.

**3. `frontend/src/components/ui/icon-names.ts`, then `Icon.tsx`.**
The `icon` you named in the definition. `Icon.tsx` is `satisfies
Record<IconName, PhosphorIcon>` so a name without a glyph fails typecheck — but
only after the name is in `ICON_NAMES`, which is a plain array and is not.

**4. `node-registry.ts` — `DEFAULT_NODE_TYPES`.**
Palette order, and the number keys: `hooks/useFlowKeyboardShortcuts.ts` indexes
this array for `1`…`9`. Left out, the block exists and nothing in the interface
can add one.

**5. `node-registry.ts` — `MODULE_NODE_TYPES`.**
`groups` and `channels` *replace* the default list rather than extending it, so
a type added only to `DEFAULT_NODE_TYPES` is absent from both. Both modules are
`comingSoon` in `features/bots/modules.ts` today, which is exactly why the
omission will not show up on screen — check the file, not the browser.

**6. `frontend/src/features/flow-builder/lib/simulate.ts`.**
The blueprint preview in the wizard and the template gallery — not the test
chat, which drives the real backend. Its `switch` ends in a `default` that
pushes `node.text` as a **bot bubble**, so an unlisted block narrates its own
card explanation at the reader as if the bot had said it. Add a case even if the
case is "print a system line and stop".

**7. `backend/apps/flows/vocabulary.py` — `NODE_TYPES`.**
The block table in Python: the type, what the palette calls it, the ports it
publishes, whether it is an entry block, whether its ports come from its own
buttons. `GET /api/flows/schema/` serialises it and
`apps/flows/graph_validation.py` refuses a saved graph that disagrees with it —
so a type missing here is a block the editor can draw and **the API will not
store**, on the autosave as well as on an import.

It is the second copy of item 2, and the pair is held together by
`backend/apps/flows/tests_vocabulary_contract.py`, which parses
`node-definitions.ts` and asserts the two agree on the set of types, each one's
fixed ports and the entry sets. That test failing is not a flaky test; it is
this list not having been walked.

**8. `backend/apps/engine/runner.py` — `_HANDLERS`.**
`execute` looks the type up here. It used to fall back to `_handle_message`,
which **delivers the block's own `text` to Telegram** as a real message — that
is fixed, and an unknown type is now stepped over with a system step instead.
Either way the block does nothing, so this is still the entry that decides
whether the block works at all.

### Only if the block does the thing

- **`backend/apps/engine/sender.py` — `TYPE_CONTENT_KINDS`** — if the block
  sends something and its *type* must overrule whatever `contentKind` a graph
  saved earlier still carries. `menu`/`subscription`/`rating`/`language`/
  `followup` map to `"text"` for that reason; `invoice` maps to itself.
- **`sender.build_keyboard`** — if the keyboard is generated by the block
  rather than drawn by the author (the gate's join rows, the stars, the
  languages, the Pay row).
- **`apps/flows/vocabulary.py` — `published_ports`** — if the block introduces
  a content kind that takes no `reply_markup` at all. This is the half that is
  easy to miss, because nothing fails: an album's keyboard is refused by
  Telegram, so a port published for a row nobody can tap becomes an exit the
  editor draws, `graph_validation` accepts and the runtime never reaches. Both
  sides gate it and both have to be told — `published_ports` and
  `backRowReachesTelegram` on one hand, `nodeButtons` and `getNodePorts` on the
  other. The rule already applied to button ports; the back row is the one that
  had to be taught it afterwards, and the cost of finding out was a session.
- **`backend/apps/engine/dispatch.py` — `_reply_port`** — if the block parks.
  This decides which exit an incoming update continues the parked run through,
  and returning `None` means "this was a new conversation, not an answer".
- **`lib/validate-graph.ts` — `BODY_REQUIRED_TYPES`** — only where an empty
  body means nothing runs. Everywhere else `text` is a label the card reads
  back and a blank one is a naming choice, not a fault.
- **`components/Inspector/fields/advanced-fields.ts` — `PRIMARY`** — the at
  most three controls the block leads with. Unranked types fall back to
  `ALWAYS_SECONDARY`, which is usually right; rank it when the fallback would
  fold away the only thing the block has (that is why `end: ["title"]` exists —
  without it the panel opened on a closed drawer and nothing else).
- **`store/graph-helpers.ts::createNode` and `node-registry.ts::createNodeDefaults`**
  — if the block carries a config object of its own. Three edits, not one: the
  `Pick<FlowNode, …>` return type, the object `createNodeDefaults` builds, and
  the conditional spread in `createNode`. Miss the last and a fresh block loses
  its defaults on creation only.
- **`components/Inspector/NodeFields.tsx`, a field component, and a
  `NodeFieldSlot`** — same condition. Fields are placed off `definition.hasX`,
  never off `node.type`; keep it that way.
- **`node-registry.ts` — `MODULE_BUTTONLESS`** — if `hasButtons` and some
  module cannot deliver that keyboard.
- **`lib/persistence.ts::migrateNode`** — if the new type supersedes an older
  shape. Graphs are upgraded as they are opened, never by a database migration
  (see the module docstring). If the old shape's edges left through a port the
  new one does not publish, move them in `migrateGraph` as the invoice
  conversion does.
- **`components/simple/step-meta.ts` — `ADD_CHOICES`** — only if it belongs
  among the six shortcut cards. Everything else reaches Simple mode through
  "Ko'proq" → `getConnectableNodeTypes`, which is already derived from the
  palette.
- **`frontend/src/features/flow-kit/recipes/*`** — if a template should use it.
  `isKnownNodeType` drops a draft the registry has no definition for and
  `isBuildableTemplate` then hides the whole template, so a recipe naming a
  half-added type makes a template quietly disappear from the gallery rather
  than crash.

## What it must stay out of

**The entry sets — two copies of the same six strings, down from three.**
`node-registry.ts::ENTRY_NODE_TYPES` is one. The backend's is
`flows/vocabulary.py` (`entry=True` on the row), and
`flows/models.py::ENTRY_NODE_TYPES` and `engine/runner.py::PASSTHROUGH_TYPES`
are both *derived* from it now rather than written out again — the contract test
holds the remaining pair together. An ordinary block put in them loses its input
dot and refuses dropped connections, `flows/services.py::derive_triggers` mints
a `FlowTrigger` from it — defaulting to `kinds: ["any"]`, a catch-all that
answers **every** message the bot receives — and `_handle_entry` runs it, which
records a step and sends nothing. A block that sends anything must not be here.

**`OWNED_ENTRY_TYPES` and `fixed: true`.** `applyEntryRule` keeps the first
block of these types in a graph and **deletes the rest on load**, from any graph
however it arrived. That is right for the one block a flow owns and catastrophic
for anything an author may add twice.

**`MessageContentKind`.** A content kind is one `send*` method inside Xabar; a
block type is a row in the palette with ports of its own. The invoice is the
worked precedent — it moved out of the content menu precisely because "how do I
charge for this" is a palette question and "was it paid" is a branch, and a
branch belongs to a block, not to a dropdown.

**`BODY_REQUIRED_TYPES`** unless an empty body genuinely produces nothing.

## Ports, after the transposition

The canvas used to run top to bottom and now runs left to right. Every exit
leaves the card's **right** edge, every incoming edge lands on the **left**, and
`NodePort` has no `side` field any more — it could only ever have held `"right"`.
`offset` is the distance **down that right edge from the card's top-left
corner**, and `portAnchor` reads it as `{x: node.x + nodeWidth(node), y: node.y +
port.offset}`.

**`bodyMiddle` is `(height − buttonRowsHeight(node)) / 2`, and everything not
tied to a button row measures from it** — the block's own exit, both halves of a
branch pair, and `nodeInputDy` on the left edge.

The middle specifically, because of the card's shape. `FlowNodeCard` sets
`borderRadius: Math.min(MAX_RADIUS, height / 2)` with `MAX_RADIUS = 30`. On the
shortest cards — 62px is the floor today, shared by `delay`, `tag`, `human`,
`flowlink`, `channelpost` and `end` — that is a 30px radius on a 62px card: the
right edge is straight for **two pixels**, from
y=30 to y=32. `bodyMiddle` is 31, dead centre of that window. Anchor a dot
anywhere else on a card that short and it floats off the border it is supposed
to straddle. The middle is the one height where a rounded card and a square one
agree, which is also why `nodeInputDy` uses it: two blocks of the same type
wired in a chain are then joined by a straight horizontal line.

Keyboard rows are subtracted rather than averaged in — a menu with six buttons
is mostly keyboard, and its "continue" exit would otherwise sit among button
dots it has nothing to do with.

**`CARD_HEADER_HEIGHT = 29`** is the icon/title row, and `branchPorts` clamps a
pair to `max(bodyMiddle, CARD_HEADER_HEIGHT + BRANCH_PORT_SPREAD / 2)` = 41. So
below 82px of block the upper exit would ride level with the title row and its
"Ha" caption would land under the pen and play controls that live there. None of
the three branching blocks is that short today (`condition` 84, `subscription`
84, `invoice` 92) — the clamp exists so the next one is not discovered on screen.
It buys that at the cost of the border straddle above, which is the right trade
only because it never fires on a real block.

`BUTTON_ROW_HEIGHT`, `BUTTON_ROWS_TOP_PAD`, `BUTTON_ROWS_BOTTOM_PAD` and
`CARD_HEADER_HEIGHT` are shared between `node-definitions.ts` and the markup in
`FlowNodeCard.tsx`, and those are the only two places that know them. Change one
and the other has to follow, or every button dot drifts off its row.

Two more:

- **A block may publish no ports at all** (`noPorts`, used by `end`). The card
  maps over the list, so it needs no special case; the input dot is not a port.
  An `out` dot wired to nothing is the wrong alternative — every other unwired
  exit on the canvas means "not finished yet", and the block whose job is to say
  "finished" must not be drawn as the thing it denies.
- **A new `NodePortKind`** must be added to `PORT_COLOR` and `PORT_GLOW` in
  `FlowNodeCard.tsx` and `BRANCH_TONE` in `simple/SimpleStepList.tsx`. All three
  are `Record<NodePortKind, …>`, so typecheck does catch this one.

Anything that rewires an `out` edge asks `hasOutPort(node)` first. An edge
leaving a port the block never published is one no walker follows and no anchor
can be found for.

## What the runtime does with it

A handler returns `(outcome, port)` where outcome is `"continue"`, `"park"` or
`"stop"`. `walk` only tests `outcome != "continue"` and returns the run
unchanged — so **a handler that parks or stops must have called `_park` or
`_finish` itself**; returning `"stop"` without finishing leaves a run hanging in
whatever status it had.

On `"continue"`, `walk` asks `flow.next_node_id(node["id"], port)` for the edge
leaving that port. `None` — nothing wired — drops out of the loop, and the tail
of `walk` calls `_finish(run, DONE)`. That is the terminal path, and there is
exactly one of it. `MAX_STEPS = 60` guards a cycle that shipped anyway.

**A block with no exit must take that same path rather than invent one.**
`_handle_end` is three lines: record the step, `_finish(DONE)`, return
`"stop"`. It says nothing extra, because a block that did would make one bot
behave two ways depending on whether the author drew the ending or let the
graph run out — a difference invisible on a canvas, which is what makes it
expensive.

There used to be a fourth line here (`offer_menu_after_flow`) and a bot setting
behind it (`Bot.settings.fallback.menuAfterFlow`, read in `engine/fallback.py`)
deciding whether a finished conversation left the customer something to tap.
The module, the settings screen and the stored key are all gone. What a
customer meets after the last block is now their own next message: `find_trigger`
looks for a flow that claims it, and where none does the bot says nothing and
`record_inbound` files the message to Suhbatlar. See the `runtime` skill, §7.

`"stop"` rather than `"continue"` for a second reason: `walk` then never looks
for an exit, so a stale `out` edge left on the block by an older save or an API
write is not followed either. The editor draws no such port; graphs do not only
come from the editor. `EndBlockTests.test_nothing_wired_past_it_runs` is that
case, written down.

Parking is the third state and belongs to blocks waiting for something outside
the process: a question waits for an answer (`WAITING`), a delay for the clock
(`SLEEPING`), an invoice for the money, a handoff for a person (`HANDOFF`). Runs
are durable and every step commits before the next begins, so parking survives
the request. If the block parks, `dispatch._reply_port` needs to know how an
incoming update maps back to one of its exits.

## Two traps already paid for

Both were introduced by adding «Tugatish» and both are fixed in the tree. Do not
reintroduce them; do repeat the reasoning for the next portless or branch-only
block.

**`portAnchor` did `ports[0]!`.** It now falls back to `nodeInputDy(node)` when
the port is not found and the block publishes none. `FlowEdgesLayer` calls it
inside a `.map` over every edge, so one stale edge on one portless block threw
and took the **entire edge layer** down — every connection on the canvas gone,
not just the bad one. Graphs arrive from templates, from older saves and through
the API, not only from this editor, so "the editor cannot draw that edge" is not
a reason it cannot exist. Drawing the stale edge somewhere visible is what lets
an author delete it.

**`reorderSimpleStep` and `spliceSimpleStep` minted `out` edges from blocks that
publish no `out` port.** Both now ask `hasOutPort` first:

- `spliceSimpleStep` only re-hands the rest of the row on through the new step
  when that step has an exit; otherwise what followed stays put and surfaces
  under "Ulanmagan qadamlar" — a state the author can see and undo, unlike an
  edge nothing will ever walk.
- `reorderSimpleStep` finds the first step in the row that closes it and refuses
  a move onto or past it, with a toast, rather than wiring the next card out of
  a port that does not exist.
- `SimpleStepList` puts the row's "+" under the branches instead of after the
  last step when that step has no `out`.

`hasOutPort` is false for two different reasons — a Shart continues out of its
named branches, a Tugatish does not continue at all — and both mean "nothing may
be appended here". Note that the comment in `useFlowEditorStore::patchNode`
still claims `"out"/"yes"/"no" always exist`; that is about button-port pruning
and is harmless there, but do not read it as a general rule.

## Verifying

```bash
cd backend && .venv/bin/python manage.py test apps --settings=config.settings.test
cd frontend && npm run typecheck && npm run lint
```

The first thing to fail on a half-added block type is
`apps/flows/tests_vocabulary_contract.py`, and it fails by name: it says which
type or which port the two applications disagree about. Fix `vocabulary.py`,
never the test.

640 backend tests pass as of writing; a change to a block type must not drop
that number. Block tests live in `backend/apps/engine/tests/test_blocks.py` —
one class per block type, sharing `tests/base.py` (`from .base import *`, which
brings the update fixtures and the seeded bot). Assert what a customer would see:
what was sent, which port continued, where the run parked or finished. Adding a
class there is part of adding a block, not a follow-up.

`TELEGRAM_OFFLINE` is forced in the test settings, Celery runs inline and the
channel layer is in-memory, so the whole path — webhook → dispatch → run →
socket — is exercised with no Redis, no broker and no network.

The stand is the last check, not the first: `.claude/skills/stend/restore.sh`,
and note that a stale Turbopack cache can serve a deleted export while both
typecheck and lint are clean.
